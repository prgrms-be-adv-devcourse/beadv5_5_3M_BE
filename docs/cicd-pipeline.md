# CI/CD 파이프라인 문서

---

## 전체 구조

파이프라인은 목적에 따라 **세 개의 독립적인 워크플로우**로 분리되어 있다.

| 워크플로우 | 트리거 | 목적 |
|------------|--------|------|
| CI (`ci.yml`) | `main`, `dev/main` 대상 PR 생성/업데이트 | 빌드 검증 |
| CD (`cd.yml`) | `main`, `dev/main` 브랜치에 push(머지) | Docker 이미지 빌드 및 EC2 배포 |
| PR Review (`pr-review.yml`) | `main`, `develop`, `dev/*` 대상 PR 생성/업데이트 | Gemini AI 코드 리뷰 |

```
PR 생성/업데이트
    ├──► CI          빌드 검증
    └──► PR Review   Gemini AI 코드 리뷰

main / dev/main 머지
    └──► CD          Docker 빌드 → EC2 배포
```

> **실제 흐름 정리**
> - CI와 CD는 별개로 동작한다. CI는 PR 단계에서 빌드만 검증하고, CD는 머지 후 배포를 담당한다.
> - 빌드 시 테스트는 실행하지 않는다. (`./gradlew build -x test`)

## CI 파이프라인

**트리거**: `main`, `dev/main` 브랜치를 대상으로 하는 PR 생성 · 업데이트 · 재오픈 시 실행. 같은 PR에 새 커밋이 push되면 이전 실행은 자동 취소된다.

### 1. 변경된 서비스 감지 → 빌드 대상 서비스를 자동으로 선별

PR의 변경 파일 목록을 분석하여 `*-service/` 디렉토리에 해당하는 서비스만 추려낸다. `build.gradle`이 없는 디렉토리나 `CLAUDE.md`, `.github/` 같은 비서비스 파일 변경은 빌드 트리거에서 제외된다.

### 2. 서비스별 병렬 빌드 → 감지된 서비스를 동시에 빌드하여 검증

변경된 서비스들을 matrix 전략으로 병렬 실행한다. Java 21 환경에서 Gradle로 빌드하며, 한 서비스가 실패해도 나머지 서비스는 계속 빌드된다. (`fail-fast: false`)

- 빌드 성공 시: JAR 아티팩트를 업로드하여 CD에서 재사용
- 빌드 실패 시: `build/reports/` 아티팩트를 업로드하여 원인 분석에 활용

### 3. 결과 리포트 → 전체 빌드 결과를 종합하여 PR에 상태 표시

변경된 서비스가 없으면 CI를 건너뛰고, 빌드에 실패한 서비스가 있으면 CI 실패로 표시한다.

## CD 파이프라인

**트리거**: `main` 또는 `dev/main` 브랜치에 push(PR 머지 포함) 시 실행.

### 1. 변경된 서비스 감지 → 이번 push에서 변경된 서비스를 선별

CI와 동일한 방식으로 변경된 서비스 목록을 추출한다. 변경된 서비스가 없으면 이후 단계를 모두 건너뛴다.

### 2. 빌드 및 아티팩트 준비 → 배포할 JAR 파일을 생성

CI와 동일하게 서비스별 병렬 빌드를 수행하고 JAR를 아티팩트로 업로드한다. 빌드에 실패한 서비스가 있으면 Docker 빌드와 배포 단계가 차단된다.

### 3. Docker 이미지 빌드 및 Docker Hub 푸시 → 배포 가능한 이미지를 만들어 레지스트리에 등록

빌드된 JAR를 내려받아 Dockerfile로 이미지를 빌드하고, Docker Hub에 두 가지 태그로 푸시한다.

- `{sha 앞 7자리}` 태그: 특정 커밋으로 롤백할 수 있도록 버전 식별
- `latest` 태그: EC2에서 항상 최신 이미지를 pull하도록 지정

### 4. EC2 배포 → 운영 서버에 새 버전 컨테이너를 기동

SSH로 EC2에 접속하여 `docker compose`로 해당 서비스만 교체 배포한다.

```bash
docker compose --profile {service} pull          # 새 이미지 내려받기
docker compose --profile {service} up -d --remove-orphans   # 컨테이너 교체
docker image prune -f || true                    # 이전 이미지 정리
```

> `|| true`: 여러 서비스가 동시에 배포될 때 `prune` 명령이 충돌하더라도 배포 자체는 실패하지 않도록 처리

### 5. 배포 결과 리포트 → 서비스별 Docker 푸시 / EC2 배포 결과를 요약

GitHub Actions Summary에 서비스별 성공/실패 현황 테이블을 기록한다.

## Gemini AI 코드 리뷰

**트리거**: `main`, `develop`, `dev/*` 브랜치를 대상으로 하는 PR 생성 · 업데이트 · 재오픈 시 실행.

사람 리뷰어가 보기 전에 AI가 코드를 먼저 분석하여 **CRITICAL 수준의 문제만** PR 코멘트로 자동 게시한다. 머지를 차단하지 않으며 참고용으로만 활용된다.

### 1. PR 생성 시 자동 트리거 → 팀원이 PR을 올리면 GitHub Actions가 자동으로 변경된 서비스를 감지

PR의 변경 파일을 분석하여 리뷰 대상 서비스 목록을 추출한다. 서비스 코드 변경이 없으면 리뷰를 건너뛴다.

### 2. 코드 변경사항 분석 → 변경된 코드의 diff를 Gemini에 전달하여 CRITICAL 이슈를 분석

서비스별 diff를 추출하고, 아래 규칙 계층에 따라 프롬프트를 조립하여 Gemini API를 호출한다.

**리뷰 규칙 계층 (`.github/review-rules/`)**

| 규칙 파일 | 적용 조건 | 주요 규칙 |
|-----------|-----------|-----------|
| `_common.yml` | 항상 적용 | SEC-001: 하드코딩된 시크릿 감지, LAYER-001: 헥사고날 레이어 경계 위반 |
| `_java-spring.yml` | diff에 `.java` 파일 포함 시 | TXN-001: `@Transactional` 내부 Kafka 발행 또는 외부 HTTP 호출 |
| `_kafka.yml` | diff에 Kafka 관련 경로 포함 시 | Kafka 관련 규칙 |
| `{service}.yml` | 해당 서비스 전용 규칙 파일 존재 시 | 서비스별 특수 규칙 |

**토큰 예산 관리**
- PR 전체 최대 입력 토큰: 100,000개 (약 400KB)
- 서비스 diff가 128KB를 초과하면 상위 30개 파일로 제한
- 누적 사용량이 한도를 초과하면 해당 서비스 리뷰를 건너뜀

**Gemini 호출 설정**
- 모델: `gemini-2.5-flash`
- 온도: `0.2` (일관된 분석을 위해 낮게 설정)
- 응답 형식: 구조화된 JSON (severity, category, file, 설명, 개선 제안)
- 429 응답 시 최대 3회까지 지수 백오프로 재시도

### 3. PR 코멘트로 피드백 → 분석 결과를 자동으로 PR 코멘트에 작성하여 사람 리뷰어 전에 1차 필터링 역할 수행

서비스별 분석 결과를 마크다운 테이블로 변환하여 PR에 코멘트를 게시한다. 같은 PR에 새 커밋이 push되면 기존 코멘트를 업데이트하여 중복 생성을 방지한다.

**심각도 수준**

| 아이콘 | 수준 | 설명 |
|--------|------|------|
| 🔴 | CRITICAL | 데이터 손상, 보안 취약점, 금융 무결성 문제 → **PR 코멘트에 게시** |
| 🟠 | HIGH | 심각한 버그 가능성 |
| 🟡 | MEDIUM | 코드 품질 개선 필요 |
| 🔵 | LOW | 스타일, 가독성 |

> Gemini에는 CRITICAL 이슈만 보고하도록 지시하므로, 실제 코멘트에는 CRITICAL 항목만 표시된다.

코멘트가 GitHub의 65,536자 제한에 근접하면(`> 60,000자`) 서비스별 findings를 `<details>` 태그로 접어서 자동으로 압축한다.
